## THE IRON LAW (gstack investigate 원칙)

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

근본 원인을 확인하지 않은 수정 제안은 무효다.
증거 없이 "아마도 ~때문일 것"이라는 가설 수정을 제안하지 말 것.

## Phase 1: 근본 원인 조사 (superpowers systematic-debugging)

### 1-1. 증상 정확한 서술
- 실제 관찰된 것 (로그, 에러 메시지, 스택 트레이스)
- 재현 가능한가? (YES/NO + 재현 조건)
- 최근 변경사항 (코드, 설정, 환경)

### 1-2. 컴포넌트 경계 진단 (다중 컴포넌트 시스템)

시스템에 여러 컴포넌트가 있다면:
```
컴포넌트 A → 입력: [데이터] / 출력: [데이터] → 정상?
컴포넌트 B → 입력: [데이터] / 출력: [데이터] → 정상?
컴포넌트 C → 입력: [데이터] / 출력: [데이터] → 정상?
```
어느 경계에서 실패가 발생하는지 먼저 특정하라.

### 1-3. 3회 실패 규칙 (gstack Iron Law)
동일한 접근법으로 3번 실패했다면:
- 현재 접근법을 즉시 중단
- "다른 접근법이 필요함" 명시
- 대안 접근법 제안 (다른 각도에서)

## Phase 2: 5 Whys 분석 (데이터 기반)

**전제**: Phase 1의 증거가 있을 때만 진행. 증거 없으면 "데이터 부족 — 추가 수집 필요" 선언.

### 5 Whys
1. Why: [증상] — 원인1: [데이터 근거]
2. Why: [원인1] — 원인2: [데이터 근거]
3. Why: [원인2] — 원인3: [데이터 근거]
4. Why: [원인3] — 원인4: [데이터 근거]
5. Why: [원인4] — **근본 원인**: [최종 판정]

**근본 원인**: (구체적, 모호하지 않게)

---

## Phase 3: 증거 기반 영향 평가

- 영향 범위: (어떤 시스템/기능이 영향받는가)
- Severity: LOW / MEDIUM / HIGH / CRITICAL
- 데이터 증거: (Phase 1에서 수집한 구체적 데이터 포인트)

---

## 출력 필수 형식

```
ROOT_CAUSE_FOUND: YES / NO (데이터 부족)
ROOT_CAUSE: [근본 원인 한 문장]
SEVERITY: LOW/MEDIUM/HIGH/CRITICAL
EVIDENCE_COUNT: N개 데이터 포인트
ALTERNATIVE_NEEDED: YES/NO (3회 실패 규칙 적용 여부)
```

근본 원인을 찾지 못한 경우:
- "추측성 수정 제안 불가" 명시
- 추가로 필요한 데이터 목록 제시
- 다른 조사 접근법 제안
