## Phase 1: CI-통과 후 프로덕션 버그 탐지 (gstack review 원칙)

아래 항목을 반드시 검토하고, 각 항목에 대해 FOUND/CLEAR 판정:

### 1-1. SQL 안전성
- Unparameterized queries, SQL injection 가능성
- ORM 우회 raw query

### 1-2. LLM Trust Boundary (gstack 고유)
- LLM 출력이 직접 exec/eval/DB write에 연결되는 경로
- 사용자 입력이 LLM 프롬프트에 주입되는 경로 (prompt injection)
- LLM 응답을 신뢰하여 권한 검증 없이 처리하는 코드

### 1-3. 조건부 사이드 이펙트 (gstack 고유)
- if/else 중 한 브랜치만 사이드 이펙트(DB write, 파일 삭제, 외부 API 호출) 처리
- 예외 경로에서 트랜잭션/롤백 누락

### 1-4. 완결성 갭 (gstack 고유)
- TODO, FIXME, placeholder, "구현 예정" 주석이 프로덕션 경로에 있는 것
- 함수/메서드가 stub으로만 구현된 것 (pass, return None, raise NotImplementedError)

## Phase 2: OWASP Top 10 보안 체크리스트

- A01 Broken Access Control: 인가 검증 누락
- A02 Cryptographic Failures: 하드코딩 시크릿, 약한 해시, 평문 전송
- A03 Injection: SQL/XSS/command injection
- A04 Insecure Design: 보안 기능 설계 누락
- A05 Security Misconfiguration: 기본 설정, 디버그 모드, 불필요한 권한
- A06 Vulnerable Components: 구식/취약한 라이브러리
- A07 Auth/Session Failures: 세션 고정, 약한 토큰
- A08 Integrity Failures: 서명 없는 코드/데이터 실행
- A09 Logging Failures: 중요 보안 이벤트 미로깅
- A10 SSRF: 서버사이드 요청 위조

## 오탐 제외 기준 (gstack CSO 원칙)
신뢰도 8/10 미만 항목은 보고하지 말 것:
- 이론적 가능성만 있고 실제 악용 경로가 없는 것
- 이미 프레임워크 레벨에서 처리된 것 (Django ORM, parameterized query 등)
- 내부 시스템 전용으로 외부 노출이 없는 것
